04 / GAMEPLAY PROGRAMMING

Technical development

My work focused on programming the character and the systems that govern interactions with the arena and other players. I built the initial Character Blueprint from scratch and refined its behavior throughout development.

01 — PLAYER MOVEMENT

Designing a physics-based movement system

Movement is central to Pouss’Plouf !. The goal was to make the character feel like it was sliding on the ice while staying responsive during encounters.

I built the character’s movement system from scratch, applying physics forces in Unreal Engine 5 instead of moving the character directly.

DESIGN PROBLEM

How can the character keep noticeable momentum while giving the player enough control over its path?

TECHNICAL APPROACH

Build a system combining interpolated direction, dynamic acceleration, applied forces, and custom deceleration.

01.1
INPUT PROCESSING

From stick input to movement vector

The system reads the player’s movement input and uses its values to build a vector representing the requested direction.

The normalization step makes the direction independent of the vector’s original magnitude. In particular, it prevents diagonal movement from producing more force than movement along a single axis.

The Move Dir Syst function uses interpolation with VInterp To to gradually turn the current direction toward the one requested by the player.

HOW IT WORKS Input Vector → Normalize → Target Direction → VInterp To → Move Direction
Gameplay impact

The interpolation with lets me tune how quickly the direction changes. This helps create the sense of momentum we wanted on the ice.

01.2
DYNAMIC ACCELERATION

Acceleration changes with speed

A constant acceleration could not produce the intended behavior of a quick start followed by a more gradual increase in speed.

I therefore built the Current Forward Speed Syst function, which uses the character’s current speed to determine how its acceleration changes.

A Map Range Clamped node maps a speed range of 500 to 1,000 to values from 55 down to 25.

The result is then used to calculate how much acceleration to add to the current value.

500 Input speed
55 Output value
→
1000 Input speed
25 Output value
BLUEPRINT CALCULATION New Acceleration = Current Acceleration + (Acceleration To Add × MapRange(Speed)) / Division Speed
Gameplay impact

This gives us a responsive character from a standing start and progressively reduces added acceleration as speed increases. Players need to plan their path further ahead at high speed.

01.3
FORCE APPLICATION

Applying movement to the character

After calculating direction and acceleration, the system builds the force vector to apply to the character.

The ZQSD Vector Clamp vector is multiplied by Current Acceleration. The result’s X and Y components are assigned to Force Vector, while the Z component stays at zero in this part of the calculation.

The resulting vector goes into Add Force on the Character Body component with Accel Change enabled.

This applies an acceleration change independently of the physics body’s mass.

APPLICATION Force XY = Input Direction × Current Acceleration Force Z = 0 Character Body → Add Force
Technical choice

Applying forces makes movement respond to the character’s physics and provides a foundation for sliding, steering, and player interactions.

01.4
DECELERATION SYSTEM

Braking when the player changes direction

The character needed to retain momentum and remain controllable, especially when the player steers against the current direction of travel.

I built a system that uses the Dot Product to compare the current movement direction with the requested direction.

The dot product result is transformed by (Dot + 1)², producing a value between 0 and 4 for two normalized directions.

This value feeds the custom braking calculation, which is then adjusted gradually with FInterp To.

DOT PRODUCT TRANSFORM Dot = -1 → (Dot + 1)² = 0 Dot = 0 → (Dot + 1)² = 1 Dot = 1 → (Dot + 1)² = 4
Playtest results

An early approach dynamically adjusted Linear Damping. Playtests showed that this made movement feel too slippery.

The Linear Damping was therefore set to a constant, while the deceleration system still adapts braking to the player’s movement input.

TECHNICAL FINDINGS

A system built for tuning

Several calculations work together to drive movement. Their parameters are exposed in Blueprints for playtest tuning. The system evolved through four successive versions.

02 — CHARACTER ROTATION

Turning the character smoothly

The rotation runs independently of force application so the character’s visual orientation can be controlled during movement.

The movement direction provides the target angle through Atan2.

An RInterp To node then gradually interpolates the current rotation toward the target orientation.

The speed of rotation can be adjusted to change visual responsiveness without making the character snap to the new heading.

03 — PLAYER COLLISIONS

Designing physical interactions between players

In Pouss’Plouf !, collisions are central to gameplay. Players need to use their speed and their path to push opponents toward holes in the arena.

I worked on an initial implementation of physical impact responses and several versions of a system for identifying who initiated a push.

DESIGN PROBLEM

How can a collision between characters produce a physical response that players can understand and find satisfying?

TECHNICAL APPROACH

Use impact information, including direction and speed, to calculate an appropriate physical response.

03.1
COLLISION DETECTION

Identifying interactions between characters

When a collision occurs, the system needs enough information to decide how the character should respond.

The Character Blueprint includes variables for impact location, movement state, and bounce state.

This information helps manage physical interactions between players.

DATA USED Collision → Impact Location → Movement State → Collision Response
03.2
PHYSICAL RESPONSE

Turning an impact into a push

I built the first version of the physical response system around impact direction and character speed.

The goal was for the push to follow from the players’ movement so their paths directly influenced encounters.

The approach also aimed to preserve a sense of sliding while keeping collisions predictable enough for players.

HOW IT WORKS Detect Impact → Analyze Direction → Account for Speed → Calculate Physical Response → Character Reaction

Collisions and game feel

04 — RESPAWN SYSTEM

Handling death and respawning

Players regularly fall through holes in the ice in Pouss’Plouf !. The respawn system needed to bring them back quickly and keep encounters moving.

I worked on death detection, respawn management, and protecting characters temporarily after they respawn.

DESIGN PROBLEM

How can a player return quickly without causing immediate collisions with the other characters?

TECHNICAL APPROACH

Combine detection of death zones, a respawn queue, spawn-point checks, and temporary immunity.

04.1
DEATH DETECTION

Detecting a player’s fall

When a character enters a death zone, an On Component Begin Overlap event starts processing the fall.

The system checks that the detected actor is a character of type BP_CharacterParent.

Checking the respawn queue also prevents the same player from being added more than once while their death is processed.

EXECUTION FLOW Begin Overlap → Cast to BP_CharacterParent → Check Respawn Queue → Process Death → Request Respawn
Technical objective

Centralize fall detection and prevent duplicate processing for the same character.

04.2
RESPAWN QUEUE

Managing the return to play

After dying, the player enters a respawn queue called Respawn Queue.

The system waits for a fixed delay before letting the character rejoin the arena.

This separates processing the death from the player’s actual return to the match.

HOW IT WORKS Character Death → Add to Respawn Queue → Respawn Delay → Find a Spawn Point → Return to Play
Gameplay impact

The respawn delay gives each fall a short-lived consequence while allowing combat to resume quickly.

04.3
SPAWN POINT SELECTION

Selecting a spawn point

The spawn points are organized by the character’s team.

The system randomly selects a point belonging to that team, then checks availability with Can Spawn.

This check takes place before returning the character to the arena.

SELECTION Identify Team → List Spawn Points → Select at Random → Check Can Spawn → Respawn
04.4
RESPAWN IMMUNITY

Temporarily protecting the player

A respawning character can appear near other players and immediately collide with them again.

To prevent this, I built a temporary immunity system that changes collisions and detects nearby characters.

I also created a custom collision channel called Fantome to give the character specific collision behavior during this period.

Technical choice

Creating a custom collision channel lets the system vary physical behavior according to the character’s state.

Combining this channel with proximity checks lets the character return to its normal state based on nearby actors as well as the immunity timer.

I developed the initial system. Parts of it changed during production.

TECHNICAL FINDINGS

A controlled return to play

The respawn system combines death detection, queue management, selection of a respawn point, and temporary protection.

The goal is to keep the pace of a fast party game while avoiding unfair respawn situations.

05 — PROTOTYPING AND ITERATION

Iterations and playtests

The initial implementations fell short of the intended feel. Feedback from external testers guided changes to movement and collisions.

01 — MOVEMENT ITERATIONS

From rigid movement to controlled sliding

Movement went through three versions: an initial velocity-based approach, a second using physics forces, and a final version refined after playtesting.

VERSION 01 / 03

Direct velocity control

The first system used Set Physics Linear Velocity, with interpolation with of direction and values for speed. The result felt too rigid. Players felt propelled across the ice and missed the intended sliding sensation.

Observed limitation: the sense of being propelled worked against the intended sliding feel.

VERSION 02 / 03

Experimenting with Add Force

I replaced the previous approach with a force applied to the physics component using Add Force, with Accel Change enabled. I wanted to see whether this would be easier to work with. The first trials quickly felt better.

INTERMEDIATE EXPERIMENT

Deceleration and dynamic Linear Damping

Before the final version, I also experimented with physics damping that varied with speed alongside direction-dependent deceleration logic. Playtests showed that this could make movement feel too slippery.

FINAL VERSION / 03

Balancing speed and braking

The final version came from a series of playtest adjustments. Depending on the feedback, the sliding, the speed, and deceleration were too strong or too weak. The Linear Damping became constant, and I kept the custom braking.

Result: after these adjustments, playtesters were satisfied with the character controls.

02 — COLLISION ITERATIONS

From physical collisions to vulnerability mechanics

Early collisions felt unfair. I refined my prototypes and experimented with additional mechanics before another developer took over and completed the system.

VERSION 01

Early collision calculations

V1 detected impacts between characters, compared movement values, and triggered a physical push. It also checked direction and bounce and used movement tiers. Despite these rules, encounters still felt too unfair to players.

VERSION 02

Prototyping additional interactions

To make encounters more interesting, I prototyped two mechanics. The vulnerability mechanic applies a penalty through a Gameplay Tag when a player hits a target with higher speed. Subsequent hits against that target become stronger. Buff Power lets players push opponents harder after a collision between teammates.

I implemented these prototypes and the logic for Gameplay Tags to test how they played. The team kept and refined both mechanics.

Remaining limitation: despite these experiments, collisions still felt unfair.

FINAL VERSION — TEAM WORK

Correcting the calculation and identifying remaining limitations

Another developer discovered that my earlier calculations used acceleration in place of speed. They corrected the error and completed the system for collisions.

After this work, collisions felt satisfying on impact. Fairness was still uneven. A slower character could still push a faster opponent.

Finding: the impacts felt better, but the competitive consistency of collisions remained a limitation in the final game.

03 — PLAYTESTS

Observe, fix, and adjust

Around six to seven playtest sessions took place during production. The development team logged most bugs, and people outside the project provided feedback on game feel.

01 — OBSERVATION

External feedback

Assess how sliding, speed, braking, and encounters feel.

02 — DEBUGGING

Team work

Log bugs, inspect Blueprints, and revise the systems involved.

03 — ITERATION

Successive adjustments

Retest changes and revise the parameters or mechanics based on the results.

PLAYTEST FINDINGS

Movement tested well. Collision fairness still needed work.

Movement adjustments led to controls that felt satisfying to playtesters. The system for collisions improved in feel and variety through iteration, although some situations still felt unfair. These results shaped the project’s technical priorities.
