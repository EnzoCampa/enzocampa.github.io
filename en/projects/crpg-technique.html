TECHNICAL BREAKDOWN / UNREAL ENGINE 5 / BLUEPRINTS

Building the movement system.

Calculate a path, rebuild it with splines, guide the character, and control an independent camera.

This page documents the prototype’s current implementation using screenshots from my Blueprints. It focuses on the current version.

02 / STRUCTURE

Two main responsibilities, two Blueprints.

Navigation and movement are handled by the Character Blueprint. Camera logic lives in BP_Camera, which has its own components and events.

Character Blueprint

Click destination, pathfinding, splines, waypoints, and movement.

BP_Camera

Free movement, locking, recentering, rotation, height, zoom, and projection modes.

03 / PATHFINDING

From a click to navigation points.

Once the target position is available, Find Path to Location Synchronously calculates a usable path on the NavMesh. The Path Points in the result form the basis of the spline.

04 / PATH RECONSTRUCTION

Rebuilding and sampling the path every 50 cm.

The NavMesh points form an initial spline. I then retrieve positions at 50 cm intervals using Get Location at Distance Along Spline, and rebuild the path from those samples.

Why add more points?

Points spaced too far apart produce an angular route instead of the intended curve.

Why limit their number?

Sampling too densely caused slowdowns. A 50 cm interval was the compromise for this prototype. The best interval depends on the use case.

Splines interpolate curves. Each interpolated position still needs to be checked for navigability, which is a general constraint of this approach.

05 / EXECUTION

Guiding the character along the path.

The system uses the array of sampled positions to guide the character with AI MoveTo. Orientation calculations also use Find Look at Rotation. In the tested prototype, the character follows the resulting curve correctly.

Technical note

In this screenshot, For Each Loop runs independently of the completion of a latent AI MoveTo call. The visible code therefore leaves the exact order of waypoint completion uncertain. The result described here comes from observing the prototype.

06 / BP_CAMERA

An independent camera system.

The ZQSD controls move BP_Camera independently of the character. A lock state follows the character and interpolates the position with VInterp To. Recentering resumes tracking.

The system also handles rotation, zoom with a normalized parameter, a spline-driven transform, orthographic and perspective modes, and camera height calculated with a Line Trace.

07 / EXPERIMENTS

Interactions, inventory, and basic crafting.

The prototype includes click interactions, resource gathering, inventory display, and basic crafting using gathered resources. These features let me experiment with other gameplay foundations within the prototype’s scope.

08 / TECHNICAL REFLECTION

What I would do differently today.

Movement and camera controls work within the tested scope. The main challenge was producing a readable curve with sufficiently fine sampling while preserving performance.

Movement logic remains heavily concentrated in the Character Blueprint. With what I know today, I would favor a clearer separation of responsibilities and reusable components. This is a retrospective assessment of an organization that emerged during prototyping.
